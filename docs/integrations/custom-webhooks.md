# Custom Webhooks

HookTrace can be used with webhook providers that are not covered by a dedicated integration guide.

If a service can send an HTTP webhook request, you can generally connect it to HookTrace by configuring a HookTrace route as the webhook destination.

```text id="c7m4qx"
Custom Webhook Provider
          │
          │ HTTP request
          ▼
    HookTrace Route
          │
          ▼
        Event
          │
          ▼
      Delivery
          │
          ▼
   Your Application
```

## Before you start

You need:

* A running HookTrace installation
* A HookTrace route
* A webhook provider that can send HTTP requests
* A destination application that can receive the webhook

For local development, you can also use a HookTrace tunnel.

## 1. Create a HookTrace route

Create a route that will receive the webhook requests from your provider.

The route acts as the public entry point for the integration.

```text id="k9p2vx"
Webhook Provider
       │
       ▼
HookTrace Route
```

Keep the route URL available for the provider configuration.

See [Routes](../concepts/routes.md).

## 2. Configure the webhook provider

Open the webhook configuration in the service you are integrating.

Set the HookTrace route URL as the webhook endpoint.

```text id="a5r8mn"
Provider
   │
   │ webhook
   ▼
HookTrace Route
```

The exact configuration depends on the provider.

Some providers may also require you to configure:

* Event types
* HTTP method
* Content type
* Authentication
* Webhook secrets
* Signature verification

Follow the provider's webhook documentation for provider-specific requirements.

## 3. Configure the delivery target

Configure the HookTrace route with the application that should ultimately receive the webhook.

```text id="w3h6kc"
Provider
   │
   ▼
HookTrace
   │
   ▼
Delivery Target
   │
   ▼
Your Application
```

This means the provider only needs to communicate with HookTrace.

HookTrace handles the subsequent delivery to your application.

## 4. Send a test webhook

Send a test webhook from the provider.

The expected flow is:

```text id="p7v4zx"
Test Webhook
     │
     ▼
HookTrace Route
     │
     ▼
   Event
     │
     ▼
  Delivery
```

Open the HookTrace dashboard and verify that the event appears.

## 5. Inspect the event

Inspect the received event in HookTrace.

Useful information includes:

* Event identifier
* Route
* Request headers
* Request payload
* Status
* Timestamp
* Delivery information

This lets you confirm exactly what HookTrace received.

## 6. Verify delivery

Once HookTrace receives the webhook, verify that it reaches your application.

Check:

1. The event exists in HookTrace.
2. A delivery was attempted.
3. Your application received the request.
4. The application returned the expected response.

If delivery fails, inspect the delivery result and retry information.

See [Deliveries](../concepts/deliveries.md) and [Retries](../concepts/retries.md).

## Request payloads

Different providers use different payload structures.

HookTrace records the incoming webhook request as an event so that you can inspect the request received from the provider.

Your destination application should process the payload according to the provider's webhook format.

Do not assume that payload fields from one provider will exist in another provider's webhook.

## Authentication

Custom webhook providers may use different authentication mechanisms.

Common approaches include:

* API keys
* Authorization headers
* Shared secrets
* Signed requests
* Provider-specific authentication

Configure authentication according to the provider's requirements.

Keep credentials and secrets private.

Do not commit webhook credentials to Git or expose them in frontend code.

## Signature verification

Some webhook providers sign their requests so that receiving applications can verify that the request came from the expected provider.

Signature schemes are provider-specific.

If your provider uses signed webhooks:

1. Follow the provider's signature documentation.
2. Preserve the required request headers.
3. Configure the corresponding HookTrace verification capability if supported.
4. Verify the signature in your destination application when appropriate.

Do not assume that a signature generated by one provider can be verified using another provider's algorithm or format.

## Local development

If your destination application is running locally, you can use a HookTrace tunnel.

```text id="q2f9hd"
Custom Provider
      │
      ▼
   HookTrace
      │
      ▼
    Tunnel
      │
      ▼
localhost
```

This allows you to test the integration without exposing your local application directly to the internet.

See [Tunnels](../concepts/tunnels.md).

## Debugging

If the webhook does not appear in HookTrace, check the provider side first:

* Is the webhook URL correct?
* Is the provider sending the expected event?
* Is the HookTrace endpoint reachable?
* Does the provider report an HTTP error?
* Is the HookTrace route configured correctly?

If the event appears in HookTrace but delivery fails, check:

* Delivery target URL
* Destination availability
* HTTP response
* Timeout behavior
* Retry status

## Replay

Once HookTrace has recorded the webhook as an event, you can replay the event when you need to send it through the delivery workflow again.

```text id="m6c8ws"
Existing Event
      │
      │ replay
      ▼
   Delivery
      │
      ▼
Your Application
```

Replay is useful after fixing a destination application or when reproducing a webhook during development.

See [Replay](../concepts/replay.md).

## Testing checklist

Before considering a custom webhook integration complete, verify:

* [ ] Provider can reach the HookTrace route.
* [ ] HookTrace receives the webhook.
* [ ] The event appears in the dashboard.
* [ ] The payload is correct.
* [ ] The delivery target is configured.
* [ ] The destination receives the request.
* [ ] The destination returns the expected response.
* [ ] Failed delivery behavior has been tested.
* [ ] Replay has been tested where appropriate.
* [ ] Secrets are stored securely.

## Provider-specific behavior

HookTrace provides the webhook infrastructure, but the provider remains responsible for its webhook format and delivery behavior.

For provider-specific details such as:

* Event types
* Payload schemas
* Authentication
* Signature verification
* Provider retry behavior
* Webhook configuration

refer to the provider's official documentation.
