# Integrations

HookTrace works with services that send webhook requests.

The integration model is provider-independent: a provider sends a webhook to a HookTrace route, HookTrace records the request as an event, and the event can then be delivered to your application.

```text
Webhook Provider
       │
       │ webhook
       ▼
 HookTrace Route
       │
       ▼
     Event
       │
       ▼
   Delivery
       │
       ▼
Your Application
```

## How integrations work

Most webhook integrations follow the same basic workflow.

### 1. Create a route

Create a HookTrace route that will receive webhook requests.

```text
Provider
   │
   ▼
HookTrace Route
```

### 2. Configure the provider

Open the provider's webhook configuration and set the HookTrace route as the webhook endpoint.

```text
Provider
   │
   │ HTTP webhook
   ▼
HookTrace
```

### 3. Receive the event

When the provider sends a webhook, HookTrace receives the request and records it as an event.

```text
Provider
   │
   ▼
HookTrace
   │
   ▼
Event
```

### 4. Deliver the event

HookTrace forwards the event to the configured delivery target.

```text
Event
   │
   ▼
Delivery
   │
   ▼
Your Application
```

### 5. Inspect and debug

Use the HookTrace dashboard to inspect the received event and its delivery status.

If delivery fails, you can investigate the failure, allow retries to occur, or replay the event after fixing the destination.

## Provider configuration

Every webhook provider has its own configuration interface and webhook requirements.

Depending on the provider, you may need to configure:

* Webhook endpoint URL
* Event types
* Request authentication
* Webhook signatures
* API credentials
* Test events
* Delivery settings

Follow the provider-specific guide for the exact configuration required.

## Webhook URL

The webhook URL used by a provider should point to the appropriate HookTrace route.

The provider sends the webhook to HookTrace rather than directly to your application:

```text
Provider
   │
   │ webhook
   ▼
HookTrace Route
   │
   │ event
   ▼
HookTrace
   │
   │ delivery
   ▼
Your Application
```

This gives HookTrace visibility into the webhook before it reaches your application.

## Testing an integration

Before relying on an integration in production, send a test webhook when the provider supports it.

A useful verification flow is:

```text
Configure Provider
       │
       ▼
Send Test Webhook
       │
       ▼
Check HookTrace Event
       │
       ▼
Check Delivery
       │
       ▼
Verify Application
```

If the event appears in HookTrace but does not reach your application, investigate the delivery configuration rather than the provider configuration.

## Debugging

When an integration is not working, determine where the request stopped.

### Provider → HookTrace

If no event appears in HookTrace:

* Check the provider webhook URL.
* Check the provider's webhook configuration.
* Check whether the provider reports a failed request.
* Confirm the HookTrace endpoint is publicly reachable when required.

### HookTrace → Application

If the event appears in HookTrace but delivery fails:

* Check the configured target.
* Check the destination application's availability.
* Inspect the delivery result.
* Check for timeout or application errors.
* Review retry behavior.

### Replaying a webhook

After fixing the destination, an existing event can be replayed rather than waiting for the provider to send another webhook.

See [Replay](../concepts/replay.md).

## Authentication and signatures

Webhook providers may use different methods to authenticate or verify webhook requests.

Examples include:

* Shared secrets
* Signature headers
* Provider-specific signing schemes
* API credentials

These mechanisms are provider-specific.

Do not assume that a signature generated by one provider can be validated using another provider's method.

Follow the provider-specific integration guide and the provider's official webhook documentation for the required verification process.

## Local development

HookTrace tunnels can be used when developing an integration locally.

The general workflow is:

```text
Webhook Provider
       │
       ▼
   HookTrace
       │
       ▼
     Tunnel
       │
       ▼
Local Application
```

See [Tunnels](../concepts/tunnels.md) for the HookTrace tunnel model.

## Custom webhook providers

HookTrace can also be used with providers that are not covered by a dedicated integration guide.

If a service can send HTTP webhook requests, the general integration workflow is:

1. Create a HookTrace route.
2. Configure the provider to send webhooks to that route.
3. Configure the HookTrace delivery target.
4. Send a test webhook.
5. Inspect the resulting event.
6. Verify delivery to your application.

See [Custom Webhooks](./custom-webhooks.md).

## Integration architecture

The provider remains responsible for generating the webhook.

HookTrace provides the infrastructure between the provider and your application:

```text
┌──────────────────┐
│ Webhook Provider │
└────────┬─────────┘
         │
         │ HTTP webhook
         ▼
┌──────────────────┐
│    HookTrace     │
│                  │
│  Route → Event   │
│       ↓          │
│    Delivery      │
│       ↓          │
│ Retry / Replay   │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Your Application  │
└──────────────────┘
```

This separation allows your application to receive webhooks through a consistent HookTrace workflow even when different providers use different webhook formats.
